오늘 수업은 배포였다. 정확히는 “배포했는데 사용자는 아무 일도 없어야 한다”를 만드는 법.

처음엔 이게 무슨 말인지 잘 와닿지 않았다. 배포는 새 버전을 내보내는 일이고, 새 버전이 나가면 당연히 잠깐은 뭔가 흔들리는 거 아닌가. 그런데 Cloud Run에는 리비전(revision)과 트래픽 비율이라는 게 있어서, 새 버전을 올려 놓고도 당장은 0%만 보내 놓을 수 있다. 확인이 끝나면 그때 100%로 돌리면 된다. 사용자는 그 사이에 이전 버전을 계속 쓴다.

이 글은 오늘 한 걸 정리한 것이다. 순서는 이렇다.

  1. 손으로 블루그린·카나리·롤백을 해 보고
  2. 같은 절차를 GitHub Actions 워크플로로 옮기고
  3. 스모크 테스트가 실패하면 전환이 막히는지 일부러 망가뜨려서 확인한다

대상은 staging(friend-agent-staging)만이다. production은 처음부터 Supabase도 로그인도 붙이지 않은 상태로 두고 손대지 않았다. 배포 실습을 하겠다고 운영 중인 서비스의 설정을 바꾸면, 실습이 아니라 사고 연습이 된다.

01먼저 용어부터

오늘 나온 말들은 대부분 “트래픽을 어디로 보낼 것인가”로 수렴한다.

용어한 줄 설명오늘 내가 쓴 자리
리비전서비스 설정과 이미지를 통째로 찍어 둔 불변 스냅샷. 배포할 때마다 새 이름(00023-siq 같은)이 붙는다전환 대상, 롤백 대상
태그특정 리비전에만 닿는 별도 주소(green---…run.app). 트래픽 비율과 무관하게 그 리비전으로 요청이 간다0% 상태의 새 리비전을 미리 확인할 때
블루그린새 버전(그린)을 0%로 띄워 검증한 뒤, 한 번에 100%로 갈아끼우는 방식손 실습 1·2회차, 워크플로
카나리새 버전에 10% → 50% → 100%처럼 비율을 나눠 천천히 보내는 방식손 실습에서 지표와 함께
트래픽 고정트래픽을 “최신 리비전”이 아니라 “이 리비전”에 묶는 것. 이후 배포가 트래픽을 못 받는다오늘 제일 조용히 나를 문 개념
스모크 테스트배포 직후 핵심 경로만 빠르게 두드려 보는 검사/health, /version
스타트업 프로브“이 리비전이 준비됐다”를 판정하는 기준. 기본값은 TCP 포트 확인오늘은 TCP 8080, 교안은 /health
원클릭 롤백버튼 하나로 이전 리비전에 100%를 되돌리는 것스테이지 5, rollback.yml

여기서 중요한 건 태그와 트래픽이 별개라는 점이다. 태그가 붙어 있어도 그 리비전은 0%일 수 있고, 트래픽이 100%인 리비전에 태그가 없을 수도 있다. 이걸 하나로 착각하면 뒤에서 한 번 크게 다친다. 오늘 실제로 다쳤다.

02손으로 해 본 블루그린

손으로 한 절차는 다섯 단계였다.

  1. 지금 요청을 받는 리비전 이름을 확인한다
  2. BANNER 환경변수만 바꾼 새 리비전을 0%로 올리고 green 태그를 붙인다
  3. 태그 URL의 /version으로 “새 리비전이 맞는지”, 원래 주소로 “이전 리비전이 계속 답하는지” 확인한다
  4. 요청 확인 스크립트를 켜 둔 채로 100% 전환한다
  5. --to-latest로 되돌리고 태그·BANNER를 지운다

두 번 해 보고 남은 숫자

같은 절차를 두 번 반복했다. 두 번째에 숫자가 더 좋아진 것도 있지만, 반대로 한 번은 실패가 났다.

회차0% 리비전전환+롤백 요청실패카나리(10→50→100)카나리 실패
1회차00023-siq + green230건0433건0
2회차00035-qos + green277건5483건0

1회차는 깔끔했다. 2회차는 롤백 직후에만 실패가 5건 몰렸다. 여기서 오늘의 삽질이 시작된다.

실패 5건의 진짜 원인

처음 의심한 건 새 리비전이었다. 롤백했으니 새 버전 문제겠지, 싶었다. 하지만 실패한 시각이 롤백한 직후 15:28:12~21에만 몰려 있었고, 그 50초 동안 이전 리비전(00017)은 트래픽이 0%라 인스턴스가 내려가 있었다.

즉, 원인은 배포가 아니라 콜드 스타트였다. 측정 스크립트(scripts/watch_requests.py)는 타임아웃이 2초인데, 50초 동안 아무 요청도 안 받던 인스턴스가 첫 요청을 받으면 2초를 넘길 수 있다. 바로 뒤에 curl로 때려 보니 0.28초에 정상 응답이 왔다.

여기서 배운 건 두 가지다.

  • 실패 0건은 “배포가 잘 됐다”가 아니라 “측정 조건까지 통과했다”는 뜻이다. 측정 도구의 타임아웃이 2초면, 2초 넘는 콜드 스타트는 배포 잘못으로 보인다.
  • 그래서 판정은 실패 시각과 이벤트 시각을 맞춰 보는 것으로 한다. 실패가 전환 시각 근처에만 몰리면 배포 문제, 전체에 흩어져 있으면 내 네트워크 문제다.

카나리는 숫자가 더 필요하다

카나리는 10% → 50% → 100%로 올리면서 각 단계에서 잠깐 기다리는 방식이다. 블루그린보다 안전해 보이지만, 요청 수가 적으면 10%의 숫자는 의미가 없다. 100건 중 10건이면 실패 1건만으로 오류율 10%가 되고, 그 1건이 우연일 수도 있다.

그래서 카나리 기준 문서(docs/canary-criteria.md)에 “머무는 시간”과 “다음 단계로 가는 조건 / 되돌리는 조건”을 미리 적어 두는 칸을 만들었다. 오늘은 손으로 하면서 실패 0건만 확인했고, 자동 판정은 만들지 않았다. 이건 남은 숙제다.

03트래픽 고정 — 오늘 제일 조용한 함정

전환할 때 이렇게 하면 편하다.

gcloud run services update-traffic friend-agent-staging --to-tags green=100

“green 태그가 붙은 리비전으로 100% 보내라”는 뜻이다. 짧고 명확해 보인다. 그런데 이렇게 하면 트래픽이 리비전이 아니라 태그에 묶인다.

다음 배포를 생각해 보자.

  1. 새 리비전을 만들고 tag: green을 붙인다 → 태그는 새 리비전으로 이동한다 (Cloud Run에서 태그 이름은 서비스 내 유일)
  2. 그런데 트래픽은 “green 태그”를 따라가고 있었으므로 → 스모크 테스트를 하기도 전에 100%가 새 리비전으로 넘어간다

0% 배포의 의미가 통째로 사라진다. 그래서 전환은 반드시 리비전 이름으로 한다.

rev=$(gcloud run services describe friend-agent-staging \
  --format="value(status.latestCreatedRevisionName)")
gcloud run services update-traffic friend-agent-staging --to-revisions "$rev=100"

직접 확인한 흔적도 있다. 1회차 정리 후 00016-vvb가 0%인데도 트래픽 목록에 남아 있었고, 2회차에서는 00019-4vj가 0%로 남아 있었다. 트래픽이 특정 리비전에 고정되면 그 리비전은 0%여도 목록에서 안 사라진다. 이걸 모르면 “왜 새 배포가 트래픽을 못 받지?”에서 한참 헤맨다.

04손 작업을 워크플로로 옮기기

자동화는 손으로 하던 절차를 옮겨 적는 일이다. 옮길 원본이 없으면 워크플로도 못 만든다. 그래서 손 실습을 먼저 한 번, 두 번 했다.

옮길 때 걸린 지점은 대부분 “콘솔에서는 눈으로 보던 정보를 명령으로 어떻게 얻는가”였다.

손으로 하던 일워크플로에서어디서 얻나
콘솔에서 지금 트래픽 받는 리비전 확인전환 전 로그로 남김status.traffic[].revisionName (percent > 0)
새 리비전 0% + 태그tag: green, no_traffic: truedeploy-cloudrun 액션 입력
태그 URL 찾기gcloud describe + jq액션 출력에는 서비스 URL만 있다
태그 URL에서 화면·/version 확인스모크 테스트 단계/version의 commit == github.sha
100% 전환update-traffic --to-revisionsstatus.latestCreatedRevisionName
콘솔에서 이전 리비전 고르기롤백 워크플로 버튼입력 또는 최신순 두 번째 리비전

deploy.yml의 단계는 이렇게 됐다.

단계하는 일실패하면
checkout / auth코드 받기, WIF로 GCP 인증 (키 파일 없음)즉시 중단
deploy-cloudrun소스 빌드 + COMMIT_SHA 주입 + 0% + green 태그새 리비전 안 생김
태그 URL 확인tag=green 항목의 url을 꺼내 output으로URL이 비면 다음 단계 실패
스모크 테스트10초 간격 최대 12회, /version 커밋 일치 + /health 200전환 단계 실행 안 됨
전환latestCreatedRevisionName으로 100%, 이전 리비전 로그트래픽 그대로

스모크 테스트를 태그 URL로 하는 게 핵심이다. 서비스 주소로 물으면 아직 이전 리비전이 답한다. 재시도를 12회 둔 이유도 있다. 새 리비전의 첫 요청은 콜드 스타트로 늦거나 502가 날 수 있다. 오늘 5건 실패로 배운 걸 그대로 넣었다.

롤백은 워크플로를 따로 만들었다. Actions 탭에서 Run workflow를 누르면 끝이다. revision을 비우면 최신순 두 번째 리비전으로 간다. 빌드도 새 인스턴스도 없이 트래픽 설정만 바꾸니 몇 초 걸린다.

05오늘 한 실수 두 개

정리라고 하면 잘된 것만 쓰기 쉬운데, 오늘 실제로 물린 건 이 두 개다.

실수 1 — production을 향해 워크플로를 만들었다

수업 요구는 staging만이었는데, 이 저장소의 deploy.yml이 service: friend-agent(production)이길래 그대로 0% 배포·스모크·전환을 붙였다. 문제는 staging과 production이 같은 파일을 쓴다는 점이었다. 그대로 머지했다면 운영 서비스에 매번 0% 리비전이 쌓이고, 첫 실행에서 트래픽이 “최신 리비전”에서 특정 리비전으로 고정됐을 것이다.

고치는 데 커밋 4개를 다시 쌓아야 했다. 브랜치 스택이라 앞 커밋을 고치면 뒤가 전부 따라온다. 지금은 워크플로 안에 friend-agent만 가리키는 줄이 하나도 없다.

실수 2 — 태그로 전환하려고 했다

위에서 쓴 그 함정이다. --to-tags green=100이 짧아서 끌렸는데, 다음 배포에서 태그가 이동하면 0% 배포가 무효가 된다. “왜 굳이 리비전 이름을 쓰지?” 싶었던 이유를 직접 겪고 나서야 알았다.

두 실수의 공통점은 “지금 눈에 보이는 상태”만 보고 결정한 것이다. 실수 1은 지금 파일이 어느 서비스를 향하는지만 봤고, 실수 2는 이번 전환만 생각하고 다음 배포를 안 봤다.

06Cloud Run이 하는 것과 내가 정하는 것

오늘 제일 오래 남을 표다.

Cloud Run이 하는 것내가 정하는 것
로드밸런서 운영, 리비전 간 트래픽 분배몇 %를 어느 리비전으로 보낼지
이전 인스턴스에 종료 신호를 보내고 정리언제 전환할지 (스모크 테스트 통과 후)
리비전을 불변으로 보관어떤 리비전을 남기고 지울지
요청을 받을 인스턴스를 늘리고 줄임최소/최대 인스턴스 수
기본 준비 판정 (TCP 포트 확인)준비됐다고 볼 기준 (스타트업 프로브)
—실패했을 때 롤백할지, 어디로 돌아갈지

마지막 두 줄이 오늘의 결론이다. Cloud Run은 “트래픽을 옮기는 일”을 책임지지만, “이 버전이 멀쩡한가”와 “문제가 생기면 어디로 돌아갈 것인가”는 대신 판단해 주지 않는다. 그래서 스모크 테스트와 롤백 버튼을 내가 만든다.

참고로 staging의 스타트업 프로브는 아직 TCP 8080이다. 그래서 /health를 503으로 망가뜨린 버전을 배포하면, Cloud Run은 “포트는 열렸네” 하고 준비 완료로 보고, 스모크 테스트 단계에서 멈춘다. 만약 프로브가 /health였다면 배포 단계에서 먼저 멈췄을 것이다. 어느 쪽이든 전환은 안 되지만, 어디서 멈추는지는 내가 정한 설정이 결정한다.

07마치며

오늘 한 걸 한 문장으로 줄이면 이렇다.

무중단 배포는 “잘 배포하는 기술”이 아니라, 새 버전을 사용자에게 보내기 전에 혼자 확인할 수 있는 상태를 만들어 두는 일이다.

0% 리비전과 태그 URL이 있어서 새 버전을 사용자 없이 먼저 볼 수 있었고, 스모크 테스트가 있어서 “봤다”를 자동 판정으로 바꿨고, 리비전 이름으로 전환해서 그 판정이 다음 배포에도 유지됐다.

남은 것 (일부러 안 한 것)

  • 카나리 자동 승격 — 10%에서 몇 분 기다린 뒤 오류율·지연을 보고 자동으로 50%, 100%로 올리는 것. 오늘은 손으로만 했다. 기준을 숫자로 정해야 해서 함부로 만들면 오히려 위험하다.
  • production 승인 게이트 — 지금 deploy.yml에는 environment:가 없어서 main 머지 즉시 실행된다. staging만 쓰는 동안은 문제 없지만, production으로 넓힐 때는 반드시 필요하다.
  • 롤백 기본값의 한계 — “최신순 두 번째 리비전”은 실패한 0% 리비전이 최신이면 엉뚱한 걸 고른다. 그때는 이름을 직접 넣어야 한다. 코드에 shortcut: 주석으로 남겨 뒀다.
  • 스키마 변경 — 두 리비전이 같은 Supabase 테이블을 함께 쓴다. reminders의 열 이름을 바꾸는 배포라면, 전환 중 새 코드와 옛 코드가 서로의 데이터를 못 보고, 롤백하면 옛 코드가 바뀐 구조를 읽는다. 열 이름 변경은 새 열 추가 → 읽기 전환 → 옛 열 삭제로 나눠야 각 단계가 롤백 가능하다.
