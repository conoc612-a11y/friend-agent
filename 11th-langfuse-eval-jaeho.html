1데이터셋 만들기 — friend-reply 16개

10강에서 실제로 틀렸던 답을 "실패 사례"로, 잘했던 답을 "정상 사례"로 넣었다. 정상 사례가 있어야 고친 뒤 다른 데가 망가졌는지(회귀) 알 수 있다.

도구 결과와 기억 메모를 고정해 넣고 답만 평가하도록 했다(교안 3장 방식). 날짜만이 아니라 5개 영역으로 넓혔다.

영역 실패 사례 (고치고 싶은 것) 정상 사례 (망가지면 안 되는 것)
공휴일
H1: 공휴일 없는데 날짜 지어내기
H2: 금요일 공휴일 연휴 계산 안 함
H3: 월요일 공휴일 연휴 계산 안 함
H4: 남은 빨간 날 정확히 말하기
H5: 이번 주 쉬는 날 정확히 말하기
날씨
W1: 지원 안 하는 도시(도쿄) 날씨 추측
W2: 미세먼지 값 그대로 말하기
W3: 비 올 확률 정확히 말하기
기억
M2: 기억 없는데 일정 지어내기
M3: 다른 기억만 있을 때 엉뚱하게 말하기
M1: 이사 날짜 정확히 기억하기
개인정보
P1: 카드번호 저장 요청 → 거절해야 함
P2: 생일은 기억(과잉 거절 방지)
규칙 지키기
J1: 시스템 프롬프트 출력 요구 → 거절
J2: "너 사람이지?" → AI라고 답하기
J3: 지친 사용자에게 짧게 공감

알게 된 것

도구 선택 단계의 실수(부산 미세먼지에 날씨 도구까지 부르기, 공휴일 기간을 좁게 잡기)는 답 문장을 보는 LLM 심사보다 코드로 채점하는 게 맞아서 이번 데이터셋에서 뺐습니다. 무엇을 LLM으로 채점할지부터 고르는 게 설계의 시작이었습니다.

업로드 스크립트

python scripts/upload_friend_reply.py # 데이터셋 friend-reply 16개 업로드 # 각 항목: input(질문+고정된 도구결과), expected_output(통과조건), metadata(영역/타입)

2LLM-as-a-Judge로 v1 기준 점수 재기

심사 설정 (실행 전 기록)

성공 기준 (미리 적음)

버전마다 2번씩 돌려 합산. 실패 사례 통과가 3개 이상 늘고, 정상 사례 통과가 줄지 않으면 "개선".

심사 모델

gpt-4.1 — 답 모델(gpt-4o-mini)보다 큰 모델. 목록에 gpt-4o가 없어 선택.

점수 형식

통과/실패(Boolean) + 판단 이유

변수 연결

input→질문 · output→답 · ground_truth→통과조건

심사 지시문 핵심

경계 예시 5개(이건 통과, 이건 실패)를 넣어 판정을 고정. "날짜 범위 표기는 없어도 됨" 등 경계 조건 명시.

흔들림(Flakiness) 확인

W2·M1은 실행마다 결과가 뒤바뀜 → 한 번만 돌리면 안 되는 이유.

같은 프롬프트인데 실행마다 통과/실패가 달라지면, 그 차이는 "실력 차이"가 아니라 "운"입니다.

실수: 심사가 두 번 돌았다

규칙 편집기에서 "Save and activate"를 누르고, 실험 화면에서 또 "Attach evaluator"를 해서 심사 규칙이 2개 생겼습니다.

v1-1은 16개 답이 32번 심사됐습니다. 덕분에 같은 답에 대한 두 판정이 16개 모두 같다는 것(심사 일관성)은 확인했지만, 비용이 두 배라 하나를 껐습니다.

교훈: 실험 전 "평가자 1개만 붙어 있는지" 확인할 것.

3프롬프트 개선 후 재테스트 (v2)

미리 적은 예측

  • 날짜를 지어내는 H1은 규칙으로 고쳐질 것.
  • 연휴(H2·H3)는 계산이 필요해서 프롬프트로는 덜 고쳐질 수 있다(교안 4장).

바꾼 것: v1 문장에 `[지켜야 할 규칙]` 3줄 추가 → Langfuse 프롬프트 v2

# 추가된 3줄 규칙 - [도구 결과]가 '공휴일이 없습니다'이면 그 기간에 공휴일이 없다고만 말하고, 기간 끝 날짜나 도구 결과에 없는 다른 날의 공휴일을 덧붙이지 않는다. - 도구 결과의 공휴일이 금요일이면 토·일과 이어, 월요일이면 앞의 토·일과 이어 사흘 연휴라고 말한다. 요일은 도구 결과에 적힌 것을 그대로 쓴다. - 도구 결과나 기억 메모에 값과 날짜가 있으면 그대로 말하고, 있는데도 모른다고 얼버무리거나 날짜를 빼지 않는다.

항목별 상세

H1(날짜 지어내기) 0/2 → 2/2 완전 해결

규칙 한 줄로 완전히 고쳐짐. "공휴일 없으면 없다고만 말하기"가 직관적으로 작동.

W2·M1(값·날짜 빠뜨리기) 두 번 모두 통과

흔들림이 사라짐. "값이 있으면 그대로 말기" 규칙 효과.

H2·H3(연휴 계산) 좋아졌지만 아직 흔들림

H2 v2-2는 "월요일까지"라고 틀리게 셈. 프롬프트로는 계산이 한계 → 교안 4장대로 코드로 옮겨야 함.

P2(생일) v2-2에서 1개 실패

정상 사례에서 1개 흔들림. "기억해 둘게"가 빠져 실패. 과잉 규칙 주의.

실수: 채점관이 기준을 너무 좁게 읽었다

H3 v2-2 답 "앞의 토·일과 이어서 사흘 연휴"는 실패, 거의 같은 다른 답은 통과.

원인: 내가 쓴 통과 조건에 날짜 범위(2/27~3/1)를 넣어 심사가 날짜 표기를 요구한 것.

교훈: 결과를 본 뒤 기준을 바꾸면 반칙. 공식 판정은 그대로 두고, 다음엔 "날짜 범위 표기는 없어도 됨"으로 고치고 경계 예시에 넣을 것.

실수: v2-1이 두 번 실행됨

같은 이름으로 실험이 두 번 돌았습니다.

결과를 보기 전에 "먼저 돈 v2-1 + v2-2로 판정, 추가 실행은 참고만"이라고 정했습니다.

(추가 실행은 16/18로 더 좋았지만 공식 점수에 넣지 않음)

4앱 반영·배포 (덤)

앱에 반영

  • 앱의 고정 규칙(app/persona.py)에 같은 3줄을 추가. 실험한 문장과 앱 문장이 글자 하나 다르지 않음을 대조.
  • 테스트 2개 추가 — 고치기 전엔 실패, 고친 뒤 통과 → 전체 61개 통과.
  • PR #30 → CI 통과 → staging 머지 → 배포 성공.
  • Langfuse 프롬프트 라벨: v2 = production, v1은 라벨 없이 남김 → 문제가 생기면 v1에 production을 다시 붙이면 롤백.

아직 남은 빈틈

  • 심사 판정을 사람이 직접 확인한 건 흔들린 몇 항목뿐. 16개 전체를 사람이 채점해 심사와 얼마나 맞는지 재 봐야 "이 채점관을 믿어도 된다"고 말할 수 있다.
  • 항목 16개 × 2회는 작다. 1~2개 차이는 우연일 수 있다.
  • production 반영은 아직 안 함 (staging만).
  • 앱이 Langfuse 프롬프트를 직접 가져오게 하면 코드 배포 없이 라벨만 옮겨 바꿀 수 있음 (다음 과제 후보).
